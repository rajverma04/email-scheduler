# Part 6 — Worker Architecture & Processing Engine (Production Deep Dive)

> **This is the most critical component of the entire backend.**
>
> The Express API only **accepts requests**.
>
> The Worker is the component that actually **executes scheduled emails**.

---

# 1. What is a Worker?

A Worker is a **background process** that continuously listens to BullMQ queues and processes jobs.

Unlike Express, a Worker **does not expose HTTP APIs**.

Instead, it performs asynchronous tasks.

In this project, its responsibility is:

```text
Receive Scheduled Job

↓

Load Email

↓

Validate State

↓

Check Rate Limit

↓

Send Email

↓

Update Database

↓

Complete Job
```

---

# 2. Why Separate Worker From Express?

Wrong Architecture

```text
                Express Server

                     │

          Schedule API

                     │

               Send Email
```

Problems

* Slow API
* API crashes affect email delivery
* Poor scalability
* Difficult retry
* Cannot run multiple workers

---

Correct Architecture

```text
              Express API

                   │

              Queue Job

────────────────────────────────

              Worker Process

                   │

              Send Email
```

Express becomes lightweight.

Workers perform heavy tasks.

# 42. Worker Best Practices

✅ Worker and API run as separate processes.

✅ Never send email inside controllers.

✅ Jobs contain only `emailId`.

✅ Always reload data from PostgreSQL.

✅ Check idempotency before SMTP.

✅ Handle every exception.

✅ Log every important event.

✅ Gracefully shut down.

✅ Keep workers stateless.

# 46. One Improvement for This Assignment

The assignment asks the user to upload a CSV containing many recipients.

Rather than creating one BullMQ job containing the entire CSV, a better design is:

```text
CSV Upload
    │
    ▼
Parse CSV
    │
    ▼
100 Recipients
    │
    ▼
Create 100 EmailSchedule Records
    │
    ▼
Create 100 BullMQ Jobs
```

This provides:

* Independent retries
* Individual status tracking
* Better dashboard visibility
* Easier cancellation
* Fine-grained error handling

This is the approach we'll follow.
