# 1. What is Concurrency?

Many people confuse **Concurrency** with **Parallelism**.

## Concurrency

Multiple jobs are **in progress** at the same time.

```text
Worker

Job1

Job2

Job3

Job4
```

The worker is managing multiple tasks simultaneously.

---

## Parallelism

Multiple CPUs actually execute tasks simultaneously.

BullMQ exposes **concurrency**, while the operating system determines actual parallel execution.

# 40. Recommended Architecture (Improved)

Instead of checking the limit **after** the worker starts processing, reserve a sending slot first.

```text
Worker
    │
    ▼
RateLimiterService
    │
    ▼
Reserve Next Slot
    │
    ▼
Allowed Now?
 ┌───────────────┐
 │ Yes           │
 ▼               ▼
Send        Future Slot
 │               │
 ▼               ▼
Complete    Move Job
```

This prevents many workers from repeatedly waking up only to discover the limit has already been reached.

---

# 41. Better Algorithm for Next Slot

Instead of thinking in **hours**, think in **timestamps**.

Maintain in Redis:

```text
next-slot:{sender}
```

Value

```text
2026-08-20T10:42:18
```

When a worker wants to send:

```text
slot = max(
    scheduledTime,
    nextAvailableSlot
)

nextAvailableSlot = slot + delayBetweenEmails
```

This preserves ordering automatically.

The hourly counter still ensures the hourly cap is respected.

# 44. Production Best Practices

✅ Never use in-memory counters.

✅ Always use Redis atomic operations.

✅ Keep workers stateless.

✅ Preserve FIFO order for each sender.

✅ Store only lightweight job data (`emailId`).

✅ Reschedule instead of failing.

✅ Calculate the next available sending slot.

✅ Make all limits configurable through environment variables.

# 46. One Important Improvement to the Earlier Design

In Parts 5–7, we described storing `delayBetweenEmails` and `hourlyLimit` on each email record. That works, but a cleaner production design is:

* Store **default limits** on the **Sender** (or organisation/tenant).
* Allow an individual scheduling request to **override** them if the UI provides custom values.
* Copy the effective values onto each email record (or campaign) so historical jobs continue using the configuration that existed when they were scheduled.

This makes the system deterministic even if sender defaults change later.
