# Part 7 — SMTP & Email Delivery Architecture (Production Deep Dive)

> **This chapter explains what happens after the BullMQ Worker decides an email is ready to be sent.**

This is where our backend interacts with the external world.

The Worker doesn't know **how** an email is sent.

Instead, it delegates that responsibility to the **SMTPService**.

---

# 1. What is SMTP?

SMTP stands for

> **Simple Mail Transfer Protocol**

It is the standard protocol used to send emails over the internet.

Our application **does not send emails directly**.

Instead, it talks to an SMTP server.

```text
Our Backend

↓

SMTP Server

↓

Recipient Mail Server

↓

Recipient Inbox
```

For this assignment

```text
Backend

↓

Ethereal SMTP

↓

Fake Inbox
```

---

# 2. Why Ethereal Email?

The assignment explicitly requires

```text
Ethereal Email
```

Ethereal is a fake SMTP provider.

Advantages

* No real emails sent
* Safe for testing
* No spam issues
* Provides preview URL
* No DNS configuration needed

Worker behaves exactly like production.

# 34. SMTPService Responsibilities

| Responsibility   | Description                                        |
| ---------------- | -------------------------------------------------- |
| Create Transport | Build Nodemailer transport from sender credentials |
| Compose Mail     | Create mail object                                 |
| Authenticate     | Verify SMTP credentials                            |
| Send Email       | Call Nodemailer                                    |
| Handle Errors    | Convert SMTP errors into application errors        |
| Return Metadata  | Message ID, response, preview URL                  |

# 35. Production Best Practices

✅ One SMTPService.

✅ Worker never imports Nodemailer directly.

✅ Credentials stored in database or secrets manager.

✅ Use connection pooling where possible.

✅ Separate temporary vs permanent failures.

✅ Configure timeouts.

✅ Log message IDs.

✅ Log preview URLs in development.

# 37. One Important Design Improvement

Instead of creating a new SMTP transport for **every email**, maintain a **transport cache**.

Example

```text
Worker

↓

sender_1

↓

Transport Cache

↓

Already Exists?

↓

Yes

↓

Reuse Transport
```

Benefits

* Faster email delivery
* Fewer TCP/TLS handshakes
* Lower SMTP server load

When a sender's credentials change, invalidate the cached transport and create a new one.

# 38. Suggested `SMTPService` Interface

The service should expose a clean API to the worker.

```text
SMTPService

├── sendEmail(emailId)

├── createTransport(sender)

├── getTransport(senderId)

├── invalidateTransport(senderId)

└── verifyConnection(senderId)
```

The worker only calls:

```text
smtpService.sendEmail(emailId)
```

Everything else remains encapsulated.
