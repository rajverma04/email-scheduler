

# Part 3 — BullMQ Architecture & Internal Working (Deep Dive)

---

# 1. What is BullMQ?

BullMQ is **not just a queue library**.

It is a **distributed job scheduling system** built on top of Redis.

Think of BullMQ as a **Task Manager**.

Instead of executing a task immediately, BullMQ stores it, waits for the right time, and hands it to workers.

Example:

```text
Schedule Email

↓

BullMQ

↓

Wait Until 10:00 AM

↓

Worker

↓

Send Email
```

Without BullMQ, your Express server would have to remember thousands of timers (`setTimeout`), which would be lost if the server restarted.

BullMQ solves this problem by persisting jobs in Redis.

---

# 2. Why BullMQ Instead of setTimeout()?

Suppose a user schedules an email for tomorrow.

Using `setTimeout()`:

```ts
setTimeout(sendEmail, 24 * 60 * 60 * 1000);
```

Problems:

❌ Lost on server restart

❌ Uses application memory

❌ Cannot scale to multiple servers

❌ Impossible to recover

❌ No retries

❌ No monitoring

---

BullMQ

```text
Create Job

↓

Store in Redis

↓

Worker waits

↓

Execute

↓

Retry if needed
```

Even if the server crashes after 10 hours, Redis still contains the job.

# 4. BullMQ Queue

The Queue is where jobs are added.

Think of it as a waiting room.

Example

```text
Email Queue

↓

Job 1

Job 2

Job 3

Job 4
```

Express API never sends emails.

It only creates jobs.

Example

```ts
emailQueue.add("send-email", jobData, {
  delay,
});
```

---

# 5. What is a Job?

A Job is a single unit of work.

One scheduled email equals one BullMQ Job.

Example

```text
Job

↓

Recipient

↓

Subject

↓

Scheduled Time

↓

Sender

↓

Email ID
```

The job should contain only the information required for processing.

Instead of storing the whole email body inside Redis, a better approach is:

```text
Job

↓

emailId
```

Worker then loads everything from PostgreSQL.

Advantages:

* Small Redis memory usage
* Database remains source of truth
* Easier updates
* Better security

---

# 6. Queue Creation

Create one queue dedicated to email processing.

```text
Email Queue

↓

send-email
```

Avoid creating multiple queues unless different workloads require isolation.

Example:

```text
email-queue
```

All scheduled email jobs go into this queue.

---

# 7. Queue Configuration

Typical configuration:

```ts
Queue(
   "email-queue",

   connection: Redis,

   defaultJobOptions:
       attempts
       backoff
       removeOnComplete
       removeOnFail
)
```

Important options:

### attempts

Maximum retry count.

Example

```text
attempts = 5
```

---

### backoff

Retry delay.

Example

```text
2 sec

↓

4 sec

↓

8 sec

↓

16 sec
```

---

### removeOnComplete

Automatically remove completed jobs.

Recommended:

```text
1000
```

Keep last 1000 completed jobs.

---

### removeOnFail

Keep failed jobs for debugging.

# 9. Delayed Jobs

This assignment explicitly requires

> No cron jobs

BullMQ provides delayed jobs.

Instead of

```text
Wait 5 hours
```

we compute

```text
delay = scheduledTime - currentTime
```

Example

Current

```text
09:00
```

Scheduled

```text
10:30
```

Delay

```text
90 minutes
```

BullMQ stores

```text
Job

↓

Delay = 90 min
```

Worker never sees it until delay expires.

---

# 11. Where Are Delayed Jobs Stored?

BullMQ stores delayed jobs inside Redis.

Conceptually:

```text
Redis

↓

Delayed Jobs

↓

Timestamp

↓

Job ID
```

Jobs are ordered by execution time.

The earliest scheduled email becomes available first.

# 12. Worker

Worker is a completely separate process.

API

```text

```

Worker

```text
Process Jobs
```

They should never be mixed.

Architecture

```text
Express

↓

Create Job

──────────────

Worker

↓

Consumes Job
```

# 13. Worker Lifecycle

Worker starts.

```text
Connect Redis

↓

Listen Queue

↓

Wait
```

No polling loops are required in your code.

BullMQ internally waits for new jobs.

When a delayed job becomes ready:

```text
Worker

↓

Receives Job

↓

Process
```

# 15. Why Does Worker Query Database Again?

Imagine

```text

↓

```

Without DB check:

```text

```

Wrong.

Correct flow:

```text

↓

Load Email

↓

Status=CANCELLED?

↓

Skip
```

Database remains authoritative.

# 18. Retry Mechanism

SMTP sometimes fails.

Reasons:

* Network timeout
* SMTP unavailable
* Temporary authentication issue
* Connection reset

BullMQ retries automatically.

```text
Attempt 1

↓

Failed

↓

Wait

↓

Attempt 2

↓

Failed

↓

Attempt 3

↓

Success
```

Worker code remains simple.

---

# 19. Backoff Strategy

Instead of retrying immediately,

BullMQ waits.

Example

```text
Retry 1

↓

2 sec

↓

Retry 2

↓

4 sec

↓

Retry 3

↓

8 sec
```

Benefits:

* Reduces provider load
* Prevents retry storms
* Improves stability

---

# 20. Concurrency

Worker can process multiple jobs simultaneously.

Example

```text
Concurrency = 5
```

Means

```text
Worker

↓

Job1

Job2

Job3

Job4

Job5
```

all processed in parallel.

The next jobs wait until a slot becomes available.

---

# 21. Multiple Workers

Suppose

```text
Worker A

Worker B

Worker C
```

All connected to Redis.

BullMQ distributes jobs automatically.

```text
Queue

↓

Job1 → Worker A

Job2 → Worker B

Job3 → Worker C
```

No duplicate processing.

This is why BullMQ scales horizontally.

---

# 22. Job Locking

Suppose

Worker A

and

Worker B

both try to process

```text
Job 100
```

BullMQ locks the job in Redis.

Result

```text
Worker A

↓

Job Locked

↓

Worker B

↓

Cannot Process
```

Exactly one worker owns a job.

---

# 23. Stalled Jobs

Imagine

Worker crashes during processing.

```text
Worker

↓

Active Job

↓

Crash
```

BullMQ detects:

```text
Lock expired

↓

Job stalled

↓

Move back to Waiting

↓

Another Worker Picks It
```

This prevents jobs from being permanently lost.

Your idempotency checks (covered later) ensure that if the email had already been sent before the crash, it is not sent twice.

---

# 24. Persistence After Restart

One of the assignment's key requirements.

Scenario:

```text
Schedule

↓

Tomorrow 10 AM

↓

Shutdown Server
```

After restart

```text
Worker reconnects

↓

Redis still has delayed job

↓

10 AM

↓

Worker receives job

↓

Email Sent
```

Nothing needs to be recreated.

BullMQ reloads state from Redis.

---

# 25. What Happens If Redis Restarts?

BullMQ depends on Redis persistence.

Redis should be configured with:

* AOF (Append Only File)
* or RDB snapshots

Without Redis persistence:

```text
Redis Restart

↓

Jobs Lost
```

For production:

```text
Redis

↓

Disk Persistence

↓

Restart Safe
```

# 29. Best Practices We'll Follow

✅ One dedicated email queue.

✅ Jobs contain `emailId`, not full email content.

✅ Worker always reloads the latest state from PostgreSQL.

✅ BullMQ manages scheduling, retries, and concurrency.

✅ PostgreSQL remains the business source of truth.

✅ Redis provides durable queue storage and coordination.

✅ Worker processes remain independent from Express API processes.
