# 1. What is Redis?

Redis (**Remote Dictionary Server**) is an **in-memory data structure store**.

Unlike PostgreSQL, Redis stores data primarily in RAM, making reads and writes extremely fast (typically sub-millisecond).

For this project Redis serves **three major purposes**:

1. BullMQ Job Storage
2. Distributed Rate Limiting
3. Distributed Coordination Between Workers

> **Important:** Redis is **not** our business database. PostgreSQL remains the source of truth.

---

# 2. Why Do We Need Redis?

Suppose we only have PostgreSQL.

User schedules an email.

```text
User

↓

Database

↓

Wait until tomorrow

↓

Send Email
```

How will the backend know **when tomorrow arrives?**

You would have to continuously poll the database.

```text
Every Second

↓

SELECT *

WHERE scheduledTime <= NOW()
```

Problems:

* Expensive
* Poor scalability
* Heavy database load
* Inefficient

BullMQ avoids this.

Instead

```text
Store Job in Redis

↓

Redis keeps timer

↓

Worker receives job exactly on time
```

# 7. Redis Persistence

Many beginners think Redis loses everything after restart.

Not necessarily.

Redis supports persistence.

Two methods:

```text
AOF

Append Only File
```

and

```text
RDB

Snapshot
```

---

# 8. AOF (Append Only File)

Redis writes every operation.

Example

```text
SET

INCR

LPUSH

ZADD
```

All commands are appended to disk.

On restart

```text
Replay Commands

↓

Restore State
```

Advantages

* Better durability
* Minimal job loss
* Recommended for BullMQ

---

# 9. RDB Snapshot

Redis occasionally saves memory.

Example

```text
10:00 Snapshot

↓

10:05 Crash

↓

Restart

↓

Restore 10:00 Snapshot
```

Recent jobs may be lost.

Suitable as backup.

Not ideal alone.

---

# 10. Production Recommendation

Use

```text
AOF

+

RDB
```

This provides:

* Better recovery
* Backup snapshots
* Minimal data loss

# 28. What If Redis Stops?

This is the most serious failure.

Without Redis

```text
No Queue

↓

No Delayed Jobs

↓

Workers Cannot Receive Jobs
```

Therefore production deployments should:

* Enable persistence
* Restart Redis automatically
* Use health checks
* Monitor memory usage

↓

# 32. Redis vs PostgreSQL Responsibilities

| Redis               | PostgreSQL      |
| ------------------- | --------------- |
| BullMQ jobs         | Users           |
| Delayed jobs        | Email schedules |
| Waiting queue       | Email body      |
| Active jobs         | Subject         |
| Worker locks        | Sender details  |
| Rate-limit counters | Email status    |
| Coordination        | Dashboard data  |
| Temporary state     | Audit history   |

**Rule to remember:**

* **Redis = Fast operational state**
* **PostgreSQL = Permanent business state**

# 33. Best Practices We'll Follow

✅ Redis persistence enabled (AOF + optional RDB snapshots).

✅ BullMQ jobs store only `emailId`.

✅ Rate limiting uses atomic Redis operations.

✅ Counters expire automatically.

✅ Multiple workers coordinate through Redis.

✅ Express remains stateless.

✅ PostgreSQL remains the source of truth.

✅ Redis is treated as an infrastructure component, not a business database.
