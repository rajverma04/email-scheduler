# 1. Project Overview

## Goal

Build a **production-ready Email Scheduling System** capable of scheduling and sending emails at scale while ensuring reliability, persistence, concurrency, rate limiting, and fault tolerance.

Unlike a simple REST API that immediately sends emails, this system separates **request handling** from **email processing**.

The backend should behave similarly to real-world email infrastructure used by companies like:

* ReachInbox
* SendGrid
* Mailgun
* Amazon SES
* Brevo

The API should only accept scheduling requests.

Actual email delivery must happen asynchronously through background workers.

---

# 2. What Problem Are We Solving?

Suppose 50,000 users schedule emails for tomorrow 9:00 AM.

If our API immediately starts sending emails:

```
Client
    │
POST /schedule
    │
Express
    │
SMTP
```

Problems:

* HTTP request waits too long.
* Request may timeout.
* Server memory increases.
* SMTP provider throttles requests.
* Difficult to recover after crashes.
* Poor scalability.

Instead, we queue the work.

```
Client
     │
POST /schedule
     │
Express API
     │
Store in Database
     │
Push Delayed Job
     │
Return 200 OK
```

Later...

```
BullMQ Worker

↓

SMTP

↓

Database Update
```

This architecture makes the system:

* Fast
* Scalable
* Reliable
* Fault-tolerant

# 6. Why BullMQ?

BullMQ is not simply a queue.

It is a distributed job scheduler.

BullMQ provides

```
Delayed Jobs

Retries

Concurrency

Persistence

Priorities

Backoff

Events

Workers

Job State Management
```

Instead of writing

```
setTimeout()

sleep()

cron()
```

BullMQ stores timing inside Redis.

---

# 7. Why Redis?

Redis acts as BullMQ's storage engine.

BullMQ stores

```
Jobs

Delayed Jobs

Waiting Jobs

Active Jobs

Completed Jobs

Failed Jobs
```

inside Redis.

Redis is extremely fast.

Millions of operations per second.

BullMQ cannot work without Redis.

---

# 8. Why PostgreSQL?

Redis is NOT permanent storage.

Database stores business data.

Example:

```
Recipient

Subject

Body

Sender

Status

Scheduled Time

Sent Time
```

Even if Redis is cleared,

Database still knows every email.

Database is the source of truth.

# 13. Responsibility of Each Folder

| Folder           | Responsibility                                                                |
| ---------------- | ----------------------------------------------------------------------------- |
| controllers      | Accept HTTP requests and return responses. No business logic.                 |
| services         | Core business logic such as scheduling, queueing, SMTP, rate limiting.        |
| repositories     | Database abstraction layer. All Prisma/SQL operations live here.              |
| queues           | BullMQ queue creation and queue events.                                       |
| workers          | Background job processors that consume BullMQ jobs.                           |
| config           | Centralised configuration for Redis, BullMQ, SMTP, DB, environment variables. |
| middleware       | Authentication, validation, logging, error handling.                          |
| validators       | Zod schemas for request validation.                                           |
| prisma           | Database schema and migrations.                                               |
| routes           | API endpoint registration.                                                    |
| utils            | Helper functions like date utilities, Redis helpers, logging utilities.       |
| dto              | Data Transfer Objects for request/response typing.                            |
| types/interfaces | Shared TypeScript types and interfaces.                                       |

# 14. Backend Design Principles

Throughout the project, we will follow these engineering principles:

* **Single Responsibility Principle (SRP):** Each class/module has one job.
* **Separation of Concerns:** API, business logic, queueing, and persistence are isolated.
* **Dependency Injection (where appropriate):** Services depend on abstractions rather than implementations.
* **Database as Source of Truth:** Redis accelerates processing but PostgreSQL stores canonical business state.
* **Asynchronous Processing:** User requests return quickly while background workers handle email delivery.
* **Idempotent Processing:** Every email is sent **at most once**, even if jobs are retried or workers restart.
* **Horizontal Scalability:** Additional API instances and workers can be added without code changes.
* **Configuration over Hardcoding:** Limits, concurrency, delays, SMTP credentials, and queue settings come from environment variables.
