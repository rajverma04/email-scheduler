# 1. Why Do We Need a Database?

Many beginners think BullMQ alone is enough because it stores jobs in Redis.

**That is incorrect.**

BullMQ is **only responsible for scheduling and executing jobs**.

It is **NOT** your business database.

Redis can tell us:

* Job waiting
* Job delayed
* Job completed
* Job failed

But Redis does **not** store business information like:

* User
* Sender
* Subject
* Body
* Campaign
* Dashboard history
* Search filters
* Analytics

Therefore we need a relational database.

---

# Why Not Single Transaction?

Database transaction cannot include Redis.

```
Database

Redis
```

are different systems.

Instead

```
Database First

↓

Redis

↓

Database Update
```

This is known as

```
Transactional Outbox Pattern (simplified)
```

In production systems, you would typically write an "outbox" record inside the same database transaction as the email schedule, then have a background process publish to BullMQ. For this assignment, it's acceptable to insert the email, enqueue the BullMQ job, and then update the record with the `bullJobId`, while ensuring failures can be recovered.

# 20. Best Practices Followed

✅ Database is the single source of truth.

✅ Redis is used only for queueing, distributed counters, and coordination.

✅ Business state is never stored only in BullMQ.

✅ Email statuses are represented with enums rather than booleans.

✅ Every relationship uses foreign keys.

✅ Dashboard queries are backed by indexes.

✅ Every table includes audit timestamps.

✅ Sender information is normalised into its own table.

✅ Retry attempts are stored separately for observability.
